做 Lovart 的这一年，Agent 能力是从零搭起来的。资产树、上下文、Skill 与工具、画布协同，一层层铺完之后，我发现真正难的不是让它跑通，而是让它稳定地变好。

每个 bad case 的处理路径都差不多：翻日志、猜原因、改一段 prompt、上线、再观察一周。一个循环两周起步，改完还可能把别的场景弄坏，因为没人说得清这次变好到底是哪一处改动带来的。

后来我意识到，这不是流程问题，是结构问题。Agent 的效果不由模型单方面决定，它由上下文供给、资产召回、能力描述、编排策略共同决定。既然效果分散在这么多层，调优也应该分散在这些层上，而且得让机器自己跑这个循环。

下面这套结构，是我按这个思路设计的。

## 一、先划三条线：什么能让它自己改

自我调优听起来很激进，落地时必须先划边界。我给自己定了三条：

**只改配置，不改代码。** 能自动改的是 prompt 片段、检索参数、Skill 描述、路由权重、超时与预算这类声明式配置。代码、计费规则、权限模型一律人审。

**不改权限边界。** 调优可以改“怎么找”，不能改“能看什么”。资产可见范围由权限树决定，Agent 自己动不了。

**每次只改一个面，并且可回滚。** 一个周期最多五个变更，每个变更带 diff 和预期指标。不满足这三条的改动不生效。

这三条看着保守，实际是把“可归因”和“可回滚”焊死在流程里。没有这两样，自动调优会迅速变成一个没人敢碰的黑盒。

## 二、七层：把 Agent 拆成能观测的层

![自我调优设计 Agent 架构](/assets/blog/arch.png)

从下往上：

**L0 模型层**，LLM Gateway，只负责多模型路由。应用层不该自己维护模型清单。

**L1 上下文层**，Context 组装。System Prompt、对话历史、记忆、资产片段各占多少预算，在这里分配。

**L2 资产层**，租户资源树、血缘、权限树。检索和召回都落在这层。

**L3 能力层**，Skill 注册表与 MCP 网关。工具怎么注册、怎么鉴权、结果怎么回写。

**L4 编排层**，Agent Loop，负责规划、调用、观测、收敛，以及把产物写进画布。

**L5 评估层**，Review Agent 加指标聚合。它既是产物质量的裁判，也是调优闭环的信号源。

**L6 治理层**，策略版本、灰度、回滚、审计。

分层的意义不在画得好看，而在于每一层都能被单独观测和单独改动。调优只发生在 L1 到 L4 的参数上，L0 的模型清单和 L6 的发布规则由人维护。

## 三、七步闭环：一轮改动怎么走

![自我调优闭环](/assets/blog/sequence.png)

1. **采集。** 每次任务落一条 trace，包含用户输入、检索到的资产、激活的 Skill、工具调用与结果、产物、用户后续动作。这一步复用现有调用日志，加字段就行，一天的工作量。

2. **判分。** 自动分来自 Review Agent 的检查项加一个裁判模型，人工分来自抽样评审。只靠点赞会样本太少，只靠模型裁判会有偏，两个都要。

3. **归因。** 这是整套东西的核心。把失败分成六类：召回缺失、技能未激活、提示歧义、工具超时、模型能力不足、预算不足。分类错了，后面全是白干。

4. **生成候选。** 针对归因结果改配置。召回缺失就调 topK 或阈值，技能未激活就改 Skill 描述，提示歧义就改 prompt 片段。

5. **离线验证。** 用历史会话加一份 golden set 回放，核心指标不下降才允许进入下一步。回放只跑采样集，不然 token 成本会失控。

6. **灰度。** 5% 流量跑 24 小时，看指标和违规率。

7. **提升或回滚。** 全量生效或者一键回滚，写审计记录。

一轮下来，从信号到生效大约几天，比人肉的两周快一个数量级。更重要的是每步都留痕，出问题能定位到具体是哪一次变更。

## 四、指标：一个北极星，三个护栏

北极星只有一个：**任务一次通过率**。用户不需要重生成、不需要大改就接受，算通过。

护栏有三个：P95 时延、单任务成本、Review 违规率。任何一项越过阈值，灰度自动回滚。

另外三个副指标决定改哪一层：召回命中率、Skill 激活率、工具成功率。它们不上报给业务，但归因时必须看。

这里有个容易忽略的点：只看一次通过率，策略会学会回避难题。难题不接，通过率自然高。所以评测集要按难度分层，同时保留抽样人工评审。

## 五、落地节奏

| 阶段 | 内容 | 工时 |
|---|---|---|
| P0 | trace 采集与回放基础设施 | 2 周 |
| P1 | 评测集、判分与归因分类 | 3 周 |
| P2 | 单点调优：prompt 与 Skill 描述 | 3 周 |
| P3 | 策略调优：检索、路由、预算 | 4 周 |
| P4 | 自动闭环与护栏 | 4 周 |

MVP 是 P0 到 P2，六到八周能跑通一条“发现问题、改配置、离线验证、灰度、生效”的链路。先跑通一条窄链路，比一次铺开五类调优更划算。

## 六、四个坑

**奖励作弊。** 指标一旦固定，策略就会绕着它走。对策是难度分层加人工抽样，别让单一数字成为唯一真相。

**过拟合线上分布。** 线上流量偏某几类设计任务，回放集如果只来自线上，调出来的策略在长尾上会更差。golden set 要定期补新场景。

**变更叠加。** 一周改五个地方，下周指标变了谁也说不清是哪一处。所以有每周期变更数上限，这不是保守，是保留归因能力。

**回放成本。** 全量回放很贵。采样集加分层抽样，能把成本压到可接受范围。

## 七、写在最后

这套结构解决的问题不是“让 Agent 更聪明”，而是“让 Agent 的变好过程可观测、可解释、可回滚”。

模型会一直换，能力会一直加，但只要分层、信号、闸门这三件事在，每次改动就都还在掌控之内。
